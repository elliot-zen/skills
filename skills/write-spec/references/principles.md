# Spec 核心原则

## 1. Agent 可复现性

最终质量标准是：一个没有历史讨论、Plan、Tasks、原开发者上下文和旧 Agent 推理过程的新 Agent，只拥有仓库与 `product.md`/`tech.md`，仍能复现语义等价的功能。

不要求代码相同，只要求产品行为、状态语义、API 语义、错误语义、数据约束和关键技术约束等价。

## 2. Living Truth

`product.md` 与 `tech.md` 只描述当前成立的事实。事实变化时直接改写当前 Spec，不在其中保留旧版本正文、失效规则、讨论过程或方案比较。完整历史由 Git 保存。

## 3. 可复现优先

规格必须让新 Agent 无需历史讨论即可实现语义等价功能。长度不是目标；影响行为、数据、副作用、权限、一致性、恢复或兼容性的事实不得因简短而删除。重复内容只保留一个权威定义并建立链接。

## 4. 事实与过程分离

记录：能力、条件→行为、状态与转换、输入输出约束、错误语义、数据约束、不变量、非目标、兼容性、当前技术约束。

不记录：推理过程、需求讨论、方案比较、临时笔记、TODO、任务列表、开发进度、Debug 流水账。

系统状态转换（如 `pending → running → succeeded`）是行为事实，必须记录；「方案 A 讨论后改成方案 B」是决策过程，必须排除。

## 5. 证据归属

每条已确认事实只有一个完整定义；其他文档链接引用。Product 和 Tech 可以分别表达同一主题的外部语义与内部约束，不得以避免重复为由省略其中一层。

## 6. 不伪造未知

事实分为 Product Facts、Technical Facts、History、Unknown。Unknown 保持未知，从代码、测试和已有文档中继续验证，不按常见实践擅自补齐业务语义。

## 7. 单一事实来源

同一事实只能有一个家。跨业务复用的公共契约（统一错误处理、HTTP 约定、认证、日志、ID 生成等）提取到公共 Spec，业务 Spec 链接引用而非复制。

提取信号是「出现第二个消费者」，不是预测未来。只有一个消费者且无项目级约定时留在业务 Spec 内；语义不同的相似规则（例如各业务不同的 Retry 策略）不强行合并。

## 8. 闭环行为

关键行为必须能回答：触发、校验、流程、数据/副作用、成功、失败，以及适用的重复、并发、超时和恢复。

## 9. Spec 优先于偶然实现

代码与 Spec 冲突时，先判断是实现偏离 Spec，还是 Spec 本身错误。只有确认系统事实已经变化才修改 Spec，不因为「代码已经这样写了」就把偶然实现固化成规格。
