# Spec 写作规则

## 1. 用可判定语句

- 反例：系统应该具有良好的稳定性。
- 正例：Scheduler 单实例异常退出不得导致已持久化任务永久丢失。

关键行为要明确、可观察、可测试、无歧义，不用模糊形容词代替规则。

## 2. 入口必须闭环

每个 API、事件、定时触发器、后台任务或外部回调至少说明：触发者/条件、输入、权限与前置校验、正常结果、数据变化、外部副作用、失败语义。重复、并发、超时、恢复仅在适用时补充。

## 3. 流程必须可执行

跨组件或多阶段流程写简洁 happy path 和关键失败分支。保留影响顺序、原子性、重试、幂等、恢复和可见性的步骤；删除代码文件、函数拆分等实现过程叙述。

## 4. 状态按需描述

存在业务状态时写状态集合、初始状态、合法转换、触发条件、转换结果、终态和非法转换。没有状态模型时写“不适用”，不要为了填模板创造状态。

## 5. 领域维度

只检查适用维度，不机械扩写：

- CRUD：字段语义、权限、校验、唯一性、修改与删除语义；
- 查询：可见范围、过滤、排序、分页、默认值和空结果；
- 配置：作用域、默认值、合法值、生效时机和兼容行为；
- 流程或异步任务：触发、状态、顺序、副作用、失败、超时和恢复；
- 外部集成：协议映射、认证、错误、Retry、Timeout、幂等和降级。

同一需求可以适用多个类别。列表用于发现缺口，不要求在文档中照抄为固定章节。

## 6. 不变量

长期必须成立的规则单独成节：

```md
- Disabled Task 不得产生新的 Execution。
- 每个 Execution 必须关联一个有效 Task。
- 一个 Execution 只能进入一个终态。
- 修改 Schedule 不得终止已运行中的 Execution。
```

不变量是新 Agent 判断实现正确性的核心依据。

## 7. 单列非目标

明确当前版本不负责的能力，限制 Agent 自行扩张实现范围。

## 8. 单列兼容性

Brownfield 项目必须说明哪些旧行为不得破坏（接口、Schema、协议、运行方式）。不要假设 Agent 知道哪些行为属于稳定契约。

## 9. 歧义处给最小示例

规则容易产生歧义时补一个最小示例澄清。示例用于澄清规则，不代替规则本身。

## 10. 禁止写入

`product.md` 与 `tech.md` 中禁止出现：推理过程、Chain of Thought、需求讨论全文、方案比较、TODO、任务列表、开发进度、实现步骤、PR 描述、Commit 记录、临时 Debug 信息、已失效事实、历史版本正文。

历史决策若形成长期约束：约束写入当前 Spec，原因摘要写入 `history.md`。
