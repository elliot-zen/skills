# Spec 写作规则

## 1. 写可判定的事实

- 反例：系统应该具有良好的稳定性。
- 正例：Scheduler 单实例异常退出不得导致已持久化任务永久丢失。

关键行为要明确、可观察、可测试、无歧义，不用模糊形容词代替规则。

## 2. 优先「条件 → 行为 → 结果」

```md
当 Cron 非法时：

- 拒绝请求
- 返回 INVALID_CRON
- 不创建 Task，不产生 Execution
```

`WHEN <condition> THE SYSTEM SHALL <behavior>` 亦可，语义清晰优先于句式。

## 3. 状态与转换必须完整

列出状态集合、初始状态、合法转换、触发条件、终态、非法转换。只列状态名称不算规格。

## 4. 单列不变量

长期必须成立的规则单独成节：

```md
- Disabled Task 不得产生新的 Execution。
- 每个 Execution 必须关联一个有效 Task。
- 一个 Execution 只能进入一个终态。
- 修改 Schedule 不得终止已运行中的 Execution。
```

不变量是新 Agent 判断实现正确性的核心依据。

## 5. 单列非目标

明确当前版本不负责的能力，限制 Agent 自行扩张实现范围。

## 6. 单列兼容性

Brownfield 项目必须说明哪些旧行为不得破坏（接口、Schema、协议、运行方式）。不要假设 Agent 知道哪些行为属于稳定契约。

## 7. 歧义处给最小示例

规则容易产生歧义时补一个最小示例澄清。示例用于澄清规则，不代替规则本身。

## 8. 禁止写入

`product.md` 与 `tech.md` 中禁止出现：推理过程、Chain of Thought、需求讨论全文、方案比较、TODO、任务列表、开发进度、实现步骤、PR 描述、Commit 记录、临时 Debug 信息、已失效事实、历史版本正文。

历史决策若形成长期约束：约束写入当前 Spec，原因摘要写入 `history.md`。
