# Spec 完整性 Review

## 事实覆盖

- [ ] 已读取项目索引、现有 Spec、相关设计文档、用户确认、实现、配置、接口和测试。
- [ ] 事实账本逐条处理：每条已确认事实都有正式文档位置、权威链接，或明确的失效/不适用理由。
- [ ] 未用中间摘要替代原始来源；没有静默丢失条件、结果、副作用、失败、边界或恢复规则。

## Product

- [ ] 每个公开入口和后台触发器都有触发条件、输入、权限/校验、成功结果、失败语义和副作用。
- [ ] 已按适用需求类型检查 CRUD、查询、配置、流程/异步任务、外部集成、权限/可见性和兼容性。
- [ ] 存在状态时，状态集合、转换、终态和非法转换完整；不存在时明确“不适用”。
- [ ] 已说明修改、删除、重复请求、空结果和边界行为（按适用情况）。
- [ ] 不变量、非目标和不得破坏的既有行为明确。

## Tech

- [ ] 组件职责、调用边界和 Source of Truth 明确。
- [ ] 数据模型、存储、协议、关键流程、原子边界和一致性规则足以复现实现。
- [ ] 并发、幂等、Retry、Timeout、失败处理、重启/恢复、部署、可观测性和性能约束已覆盖（不适用项明确）。
- [ ] 外部依赖有本地接口快照；引用可解析且包含本系统实际使用的字段和错误约束。

## 可复现性测试

只给新 Agent 仓库、`product.md` 和 `tech.md`，检查它能否不猜测地回答：

- 谁在什么条件下触发每个入口？
- 正常路径的顺序、数据变化和外部副作用是什么？
- 失败、重复、并发、超时和恢复时分别发生什么？
- 谁能访问或看到哪些数据？默认值和生效时机是什么？
- 哪些组件和数据源负责什么？哪些行为绝不能改变？

每个回答必须能指向具体章节、表格或权威链接；只能靠猜测回答则 Review 不通过。
