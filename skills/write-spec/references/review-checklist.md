# Spec Review Checklist

完成 Spec 后必须做一次可复现性 Review。

## 结构

- [ ] 使用 `docs/biz/<id>/` 或 `docs/biz/common/<id>/`，`<id>` 简短、稳定、按业务概念命名
- [ ] `product.md`、`tech.md` 存在，需要时 `history.md` 存在
- [ ] 一个 Spec 只覆盖一个相对独立的业务能力，未堆成巨型 Spec

## 内容

- [ ] Product：能力、核心实体、输入输出、状态与转换、正常/修改/删除/重复请求/边界行为、错误语义、不变量、非目标、兼容性
- [ ] Tech：组件与职责、Source of Truth、数据模型、存储、协议、并发、一致性、幂等、Retry、Timeout、失败处理、部署、可观测性、性能、技术兼容性
- [ ] 不适用的条目明确写「不适用」，不机械填充无意义章节
- [ ] 每个实现关键决策在 `tech.md` 写清或链接到权威设计文档/公共 Spec，且引用的文档与锚点可解析
- [ ] 每个依赖的外部接口均已将复现所需的定义保存到对应 Spec 的 `references/`，且 `tech.md` 链接该本地文件；快照记录原始 URL、版本或获取日期、相关章节/操作及其约束的主题
- [ ] 只描述当前事实，未混入推理、讨论、Task、开发进度
- [ ] 未用模糊形容词代替明确规则，Unknown 未被写成确定事实
- [ ] 无无意义重复，Product 与 Tech 边界清晰
- [ ] 复杂规则在需要时提供最小示例
- [ ] 当前事实未被埋在 `history.md` 中

## 公共事实

- [ ] 跨业务复用的公共契约（错误处理、HTTP 约定、认证、日志等）已提取到 `docs/biz/common/`，未在多个 Spec 中重复定义
- [ ] 业务 Spec 通过链接引用公共 Spec，未复制其契约
- [ ] 业务偏离公共约定处已显式声明例外及差异
- [ ] 公共 Spec 与业务 Spec 无冲突
- [ ] 未为只有一个消费者的事实提前抽象

## 可复现性测试

假设删除 Chat History、Plan、Tasks、原开发者上下文和旧 Agent 推理过程，新 Agent 只拥有 Repository、`product.md`、`tech.md`。它能否明确回答：

- [ ] 要实现什么？不实现什么？
- [ ] 核心实体是什么？输入输出是什么？
- [ ] 有哪些状态？状态如何变化？
- [ ] 正常情况下发生什么？失败时？重复请求时？并发时？
- [ ] 各组件负责什么？哪个存储或组件是 Source of Truth？
- [ ] 一致性、Retry、Timeout、幂等如何处理？
- [ ] 哪些行为绝对不能改变？哪些规则必须始终成立？
- [ ] 若外部文档站点不可访问，是否仍能通过 `tech.md` 的本地引用获得完整的必要接口定义及其依赖的公共定义？

关键问题只能靠猜测得到答案，则 Spec 不完整。

## 最终判断

> 删除开发过程信息后，功能语义仍然完整；换一个具备足够能力的 Agent，仍能根据当前 Spec 复现语义等价的功能。
