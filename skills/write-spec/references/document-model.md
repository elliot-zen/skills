# Spec 文档模型

## 布局

```text
docs/
├── documentation-guide.md   # 项目级文档规范（若存在）
├── common/
│   └── <id>/
│       ├── product.md
│       ├── tech.md
│       └── history.md
└── biz/
    └── <id>/
        ├── product.md
        ├── tech.md
        └── history.md
```

`<id>` 简短、稳定、按业务概念命名。一个 Spec 只覆盖一个相对独立的业务能力，不为了减少文件数量堆成巨型 Spec。

`documentation-guide.md` 记录项目级约定：文档目录、命名规则、Spec 存放位置、各类文档的职责边界。若项目没有，按本 Skill 的默认布局执行。

## 事实归属判断

> 改变这个事实，会不会改变用户或调用方可观察到的行为？

会 → `product.md`；不会，只影响实现方式或架构约束 → `tech.md`。

两层都涉及时不复制内容：`product.md` 写行为语义，`tech.md` 写实现方式。

例：

```text
Cron 非法时不创建 Task          → product.md
Task Definition 以 PostgreSQL 为准 → tech.md
```

## product.md

回答：这个功能对用户、调用方或其他系统表现为什么？

内容：能力、核心实体、输入输出、行为、状态与转换、校验规则、错误语义、不变量、边界情况、非目标、兼容性。

不包含纯实现细节（数据库、Redis Key、具体库、表结构拆分、队列中间件），除非该技术本身已成为外部契约。

## tech.md

回答：为了复现当前系统，技术实现必须满足哪些事实和约束？

内容：组件与职责、技术选型、Source of Truth、数据模型、存储、协议、并发、一致性、幂等、Retry、Timeout、失败处理、部署、可观测性、性能、技术兼容性。

记录当前技术事实，不记录完整选型讨论过程。

## 复用仓库已有设计文档

写 `tech.md` 前，先在仓库中查找文档索引、架构总览、权威设计文档和 `docs/common/` 公共 Spec。`tech.md` 是实现入口，不是这些文档的替代品：

- 链接实现所需的外部文档，说明其负责的主题以及本 Spec 如何使用。
- 不复制外部文档拥有的契约、算法、Schema 或长篇解释。
- 每个实现关键决策要么在 `tech.md` 中完整写清，要么能通过链接到达。
- 链接与 Spec 冲突时解决冲突，不要并存两条规则。

## 公共 Spec（docs/common/）

放置跨业务共享的契约与约定：统一错误处理、HTTP/协议约定、认证与鉴权、日志与追踪、ID 生成、配置与开关等。使用与业务 Spec 相同的 product/tech/history 结构；纯内部约定可让 `product.md` 写「不适用」。

### 提取时机

出现以下任一情况时，把事实提取到公共 Spec：

- 同一事实被第二个 Spec 需要（规则二）。
- 它是项目级约定，适用于所有或大多数能力。

不要提前抽象：只有一个消费者、且无明确跨能力约定时，留在业务 Spec 内；语义不同的相似规则（例如各业务不同的 Retry 策略）不强行合并。

### 引用方式

- 公共 Spec 是该事实的唯一来源。
- 业务 Spec 在 `tech.md` 的「相关设计文档与公共 Spec」表中链接它，不复述其内容。
- 业务需要偏离公共约定时，在该业务 Spec 中显式声明例外及差异，不静默复制后改写。
- 公共 Spec 与业务 Spec 冲突时，以公共 Spec 为准并消除冲突，不并存两条规则。

## history.md

回答：当前规格为什么发生过重要变化？

记录时间、变化内容、原因。它不是当前事实来源，当前行为始终以 `product.md` 和 `tech.md` 为准。

不记录：Commit Log、开发日报、Debug 日志、TODO、Agent 思考过程、PR 全文。
