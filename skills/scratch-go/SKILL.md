# Go 后端工程开发指南

## 1. 适用范围与工作流程

本手册适用于 Go 服务、后台任务程序（Worker）和命令行程序（CLI）。通用工程规范持续适用；HTTP、外部依赖和部署要求按项目实际能力适用。

“必须”“不得”表示硬性要求；未加限定的规范性陈述同样需要落实。“默认”表示无既有约定或业务特例时采用的方案；调整时说明原因，并同步契约与测试。“例如”仅用于说明，不要求创建示例中的业务或依赖。

开始工作前读取项目的 `AGENTS.md`、相关源码、测试、依赖与 Makefile，确认现有契约、版本及用户修改。既有约定优先，保留已有文件和用户修改，仅合并当前任务所需能力。调整约定时明确影响，并同步实现、测试和文档。

| 任务 | 阅读与执行顺序 |
| --- | --- |
| 开发、修复与重构 | 第 2 章通用规范 → 第 3、4 章相关能力 → 第 6 章验证 |
| 新项目初始化 | 第 5.1、5.2 节确定版本与文件 → 第 2–4 章实现适用能力 → 服务项目按第 5.3 节部署 → 第 6 章验证 |
| 配置或部署变更 | 第 3.1、3.2 节配置 → 第 5.3 节部署 → 第 6 章验证 |
| 代码审查 | 依据适用章节检查真实行为、兼容性及验证证据 |

## 2. 通用工程规范

### 2.1 组织、依赖与表达

按职责和内聚性组织包；每个可执行程序的入口位于 `cmd/<command>/`，内部实现在 `internal/`。服务程序按服务名命名，例如 `cmd/orders/`；Worker 或工具按职责命名，例如 `cmd/orders-worker/`、`cmd/migrate/`。每个入口都是独立的 `package main`，仅在需要独立程序时增加目录。

业务规则不依赖 `*gin.Context` 或数据库驱动细节，按实际职责划分模块，不强制固定分层架构。

显式构造依赖，避免可变全局状态和万能 `common/utils/base` 包。默认使用具体类型；真实调用方需要隔离或替换行为时，在使用方声明最小接口。只导出实际需要的标识符。

遵循 Go 命名与格式惯例，保持函数职责清晰，不采用机械行数门槛。人工编写的源码注释使用英文，仅说明必要的公开契约、设计原因、不变量及关键限制。

### 2.2 应用错误与传播

#### 2.2.1 错误模型与定义归属

在 `internal/apperror/error.go` 中集中实现应用错误类型、构造方法、错误链及通用错误。状态码与业务错误码分别表达协议结果和业务原因：

| 信息 | 含义 |
| --- | --- |
| `Code` | HTTP 错误状态码，使用 4xx/5xx |
| `Reason` | 稳定业务错误码，使用大写下划线格式，如 `ORDER_ALREADY_PAID` |
| `Message` | 面向调用方的可读描述 |
| `Metadata` | 可选的补充信息，类型为 `map[string]string` |
| `cause` | 可选的内部原因，通过错误链保留，不进入响应 |

字段私有存储，通过只读方法访问。提供 `New(code, reason, message)`、`WithCause(error)`、`WithMetadata(map[string]string)`，实现 `Error()`、`Unwrap()` 和 `Is(error)`。

附加原因或元数据时返回新对象；元数据在传入和对外读取时均复制，避免跨请求共享可变状态。`errors.Is` 按 `Code + Reason` 匹配，忽略描述、元数据及对象地址；`errors.As` 提取应用错误，两者均支持 `%w` 包装。

业务模块在自己的 `errors.go` 中集中定义 Reason 常量和具名构造函数，例如 `order.ErrorOrderAlreadyPaid()` 返回 `409 / ORDER_ALREADY_PAID`，不为每种业务错误另建结构体，不在调用点散写码值。确有调用方需要时提供 `IsOrderAlreadyPaid(err)` 等判断函数。

Reason 在应用内唯一，业务码带模块前缀；通用码由 apperror 维护，定义后固定状态分类，发布后不随重构改名、复用或改变含义。Message 可调整，不用于程序分支判断。

Metadata 仅承载有界的补充数据，键、含义和边界由接口契约说明并测试；复杂结构另行定义。

应用错误不依赖 Gin，`request_id` 由 HTTP 出口附加；Worker、CLI 按自身协议输出。

文件路径用于说明职责归属，业务模块出现时才创建其错误定义文件。

#### 2.2.2 传播、转换与最终处理

常规失败返回 `error`，不使用 panic；不无理由忽略错误。使用 `errors.Is/As` 判断，不比较错误字符串。在提供新诊断信息的边界补充操作上下文，需要保留原因时使用 `%w`；转换成应用错误时通过 `WithCause` 保留内部原因。

仅在语义明确的边界转换技术错误：确认记录不存在才能转为业务未找到，确认特定唯一约束冲突才能转为相应业务冲突；数据库断连等技术故障不能转换为业务拒绝。业务层返回 error，HTTP 层按第 4.1 节统一输出，不由各处理器各自拼接错误响应。

仅返回错误的函数不同时记录 ERROR，由 HTTP、任务或启动的最终处理边界记录一次。预期业务拒绝不自动记 ERROR；非预期失败、panic 和最终 5xx 记录一次 ERROR，不能仅凭自定义错误类型判断为预期失败。HTTP 的取消、响应已提交等特殊结果按第 4.1.4 节处理。

外部依赖的交互日志、重试和降级见第 3.3 节。

### 2.3 日志与故障定位

新项目默认使用 `slog.JSONHandler` 输出到 stdout，一条事件一行 JSON；已有项目沿用能满足下述要求的结构化日志方案。HTTP 服务将服务器内部日志接入结构化输出；Gin 模式见第 4.2 节。

| 信息 | 要求 |
| --- | --- |
| 服务身份 | 基础日志记录器附 `service`、`version`；`cmd/<command>` 定义构建可赋值的 `version`，开发允许 `dev`，发布使用可追溯标识 |
| 失败事件 | `time`、`level`、`msg`、稳定的 `operation`、可诊断的 `error`；应用错误附 `code` 和 `reason` |
| HTTP 关联 | 显式附 `request_id`、`method`、路由模板 `route`；取值规则见第 4.2 节 |
| HTTP 完成事件 | `status`、`outcome`、`duration_ms`；完成边界与取值见第 4.2 节 |
| 依赖与分类 | 已知依赖提供 `dependency`，可可靠分类时提供 `error_kind`；任务按需附 `job_id` |
| panic 定位 | 记录 panic 类型和恢复点捕获的 `stack`，包含实际处理器函数、源码文件及行号 |

普通错误无需全量堆栈。`slog.*Context` 不会自动附加请求 ID，`AddSource` 也不代表原始故障位置。

外部错误按依赖保留可诊断的原因，不能一律抹成 `internal error`。访问日志不重复附带终结失败详情。第三方 HTTP 调用按第 3.3.3 节使用同一日志记录器的有效级别记录交互。

### 2.4 上下文、并发与资源

可取消操作以 `ctx context.Context` 为首参并沿调用链传递，业务层使用标准上下文。不随意用 `context.Background()` 替换请求上下文；不用上下文传递业务参数或长期保存请求上下文，也不跨请求保留 `*gin.Context`。

释放创建的取消函数；每个 goroutine 都有所有者、退出条件和等待机制，共享状态正确同步。

明确文件、响应体、连接和事务的清理责任，覆盖成功、失败与取消路径，检查有意义的 `Close`、`Commit` 错误。

## 3. 配置与外部依赖

### 3.1 默认配置与环境变量

新项目只维护一份 `configs/config.yaml`，提交 Git，列出应用实际支持的配置项和默认值。开发、测试和生产使用同一文件，各环境仅通过环境变量覆盖。默认值集中维护在该文件，Go 代码和 Compose 不重复设置。配置从固定路径读取，作为外部文件交付。

启动顺序固定为：读取 `configs/config.yaml` → 应用环境变量覆盖 → 校验最终配置 → 组装依赖并启动。路径相对于进程工作目录；本地从项目根目录启动，容器工作目录固定为 `/app`，配置复制到 `/app/configs/config.yaml`。文件是运行所需交付物，不自动搜索其他路径，也不在文件缺失时静默使用代码默认值。

由 `internal/config` 提供强类型配置及加载、解析和校验能力，入口调用一次并将所需配置显式传给依赖。业务代码不自行读取环境变量，不使用可变全局配置。配置或环境变量变更后重启进程。

环境变量采用大写下划线命名，为每个可覆盖字段维护明确、唯一的映射；避免嵌套字段扁平化后重名。只读取声明支持的变量，不把进程中其他环境变量当作配置错误。HTTP 服务至少提供下列配置；Worker/CLI 仅保留适用项，后续依赖按实际需要增加：

| YAML 字段 | 环境变量 | 默认值 |
| --- | --- | --- |
| `http.addr` | `HTTP_ADDR` | `:8080` |
| `http.read_header_timeout` | `HTTP_READ_HEADER_TIMEOUT` | `5s` |
| `http.read_timeout` | `HTTP_READ_TIMEOUT` | `15s` |
| `http.write_timeout` | `HTTP_WRITE_TIMEOUT` | `15s` |
| `http.idle_timeout` | `HTTP_IDLE_TIMEOUT` | `60s` |
| `shutdown.timeout` | `SHUTDOWN_TIMEOUT` | `10s` |
| `log.level` | `LOG_LEVEL` | `info` |

配置解析与校验遵守以下规则：

- 严格解析 YAML，拒绝未知字段、重复键、类型错误和多份 YAML 文档。使用固定版本的解析依赖，明确解析时长的行为。
- 使用 `os.LookupEnv` 区分未设置和设置为空。未设置保留文件值；显式空字符串、`false`、`0` 都参与覆盖，再按字段约束校验，不能按零值判断是否提供配置。
- 时长使用 `5s`、`1m` 等 Go duration 格式，布尔值和数值按声明类型解析。HTTP 超时及关闭期限默认要求大于零；流式业务需要禁用某项超时时，应明确调整该字段契约和测试。
- 文件缺失或格式错误、环境变量解析失败、最终配置缺少必填项或不满足范围和跨字段约束时，启动失败并返回非零退出码，不静默回退。日志级别限定为 `debug/info/warn/error`，监听地址按服务要求校验。
- 密码、令牌等不保存真实默认值，由环境变量注入；依赖启用时校验对应秘密必填。诊断指出字段或环境变量名称及来源。

README 维护字段、环境变量、用途、默认值及约束清单。

### 3.2 开发环境

应用不自动加载 `.env`。开发入口 `make dev` 在构建后通过 POSIX shell 读取项目根目录的 `.env`，将变量导出给前台运行的程序。文件不存在时使用继承的环境变量和 YAML 配置，读取或执行失败时不启动程序。

`.env` 中的同名赋值覆盖继承的环境变量，未赋值的变量保留原值。需要直接使用命令行环境覆盖时运行 `make run`，例如 `HTTP_ADDR=:8081 LOG_LEVEL=debug make run`；该目标不读取 `.env`。README 提供两种启动方式的示例。

`.env` 是通过 shell 的 `.` 加载的可信本地文件，采用 `KEY=value` 赋值语法。含空格、`#` 或字面量 `$` 的值使用单引号，不写命令或命令替换；不承诺支持所有 dotenv 扩展语法。仅填写必要的开发覆盖项。

初始化时提供不含秘密的 `.env.example`，实际 `.env` 加入 `.gitignore` 和 `.dockerignore`。`.env` 在构建后加载，不负责设置 `SERVICE`、`VERSION` 或构建工具参数。

### 3.3 外部依赖调用

本节适用于实际引入的数据库、Redis、第三方 HTTP 等依赖，不预建适配层或配置。

#### 3.3.1 适配边界与资源生命周期

入口读取配置并构造依赖，适配层提供业务所需能力。按 SDK 契约复用并发安全的客户端和连接池，不逐请求创建 `http.Client`、`http.Transport` 或数据库连接池。

调用传递调用方上下文，并明确调用期限；SDK 不支持上下文时配置其自身超时并说明取消限制。响应体、`Rows`、事务等由创建或取得资源的调用方负责结束。

启动中途失败时清理已创建资源。关闭时先停止接收工作、等待在途任务，再关闭依赖客户端和连接池，遵守程序关闭期限。

#### 3.3.2 调用期限与阶段超时

每个依赖在 `configs/config.yaml` 的 `dependencies.<name>` 下维护配置，并按第 3.1 节提供显式环境变量映射，例如 `dependencies.payment.timeout` 对应 `DEPENDENCIES_PAYMENT_TIMEOUT`；README 和 Compose 同步映射。普通第三方 HTTP 调用采用以下默认值，按第三方契约调整，时长必须大于零：

| 配置项 | 默认值 | 含义及实现位置 |
| --- | --- | --- |
| `timeout` | `15s` | 一次逻辑调用的总预算，通过上下文覆盖等待连接、各次尝试、重试退避、请求写入及响应体读取 |
| `dial_timeout` | `3s` | `net.Dialer.Timeout`，限制连接建立及拨号阶段的名称解析 |
| `tls_handshake_timeout` | `3s` | `http.Transport.TLSHandshakeTimeout`，限制 TLS 握手 |
| `response_header_timeout` | `10s` | `http.Transport.ResponseHeaderTimeout`，限制请求写完后等待响应头的时间 |
| `idle_conn_timeout` | `90s` | `http.Transport.IdleConnTimeout`，控制空闲连接保留时间，不属于单次调用期限 |

总预算从逻辑调用开始计时；调用方已有更短期限时，以更短期限为准，各阶段和重试共用剩余预算。请求写入与响应体读取受总上下文控制；标准 `http.Transport` 不提供独立的通用请求写入超时字段。

收到响应头不代表调用完成，取消函数的生命周期必须覆盖响应体读取和关闭。流式接口单独声明期限及完成条件。数据库和其他 SDK 按实际支持的调用、连接等超时参数配置。

#### 3.3.3 第三方 HTTP 请求与响应日志

复用统一的 HTTP 适配及日志能力。可通过 `http.RoundTripper` 包装器捕获传输信息，由适配层结合响应体读取和解析结果完成记录。日志使用应用 `log.level`，不增加独立的报文日志开关：

| 有效级别 | 每次实际尝试的日志 |
| --- | --- |
| DEBUG | `dependency.request` 和 `dependency.response` 两条 DEBUG 事件：请求事件记录地址、方法、请求头及完整普通文本请求体；完成事件记录状态、响应头及完整普通文本响应体、耗时和结果；不额外输出 INFO 摘要 |
| INFO | 结束时只输出一条 `dependency.call` INFO 摘要，包含下表字段 |
| WARN / ERROR | 不输出上述常规交互日志；最终失败日志仍按第 2.2 节处理 |

按日志记录器的 `Enabled` 判断选择 DEBUG 或 INFO 路径，不能同时输出两套事件；未启用的级别不捕获或格式化报文。日志阶段与级别在一次尝试内保持一致。重试的每次尝试分别记录，使用同一逻辑调用 ID 和递增的尝试次数。

| 字段 | 约定 |
| --- | --- |
| `dependency`、`operation` | 第三方系统名称及稳定操作名 |
| `request_id`、`call_id` | 存在上游请求时附 request_id；每次逻辑调用生成独立 call_id |
| `attempt` | 从 1 开始的尝试次数 |
| `method`、`url` | 实际请求方式及完整目标地址，包括查询参数 |
| `request`、`response` | 请求体和响应体的文本内容；INFO 按下述规则截断，DEBUG 普通文本完整记录 |
| `status` | 实际取得的 HTTP 状态；未取得响应时省略，不伪造 0 或 500 |
| `duration_ms` | 本次尝试从开始到响应体处理结束或失败的耗时，使用单调时间计算 |
| `outcome` | `success`、`failure`、`timeout`、`canceled`；按传输和第三方业务契约综合判定，不能仅凭取得响应头或 HTTP 200 判断成功 |
| `error` | 失败原因，成功时省略 |
| `request_truncated`、`response_truncated` | 是否因摘要长度上限截断 |
| `response_complete` | 响应体是否完整取得；未取得响应或中途读取失败、取消、提前关闭时为 false |

INFO 的 request、response 各保留前 1024 个 Unicode 字符，按码点计数，不切断 UTF-8 字符；超过上限设置相应 truncated=true。摘要作为 JSON 字符串字段输出，不要求其中的截断内容仍是合法 JSON。捕获时只保存有限前缀及判断截断所需的状态，不能完整缓存报文后再截断；这是日志长度限制，不是业务报文大小限制。

文件、二进制和流式内容记录类型、已处理字节数等描述，不为日志提前读取或整体缓冲流；未读取完整时如实标记。捕获日志不得改变请求字节、消耗业务要读取的响应体，或破坏关闭、取消和重试重放语义。

超时、取消、连接失败、响应读取或解析失败都应产生完成事件；取得部分响应时记录已取得内容及完成标记。每次尝试只完成记录一次，不因 EOF、关闭和异常处理重复输出。

#### 3.3.4 错误、重试与降级

适配层识别 SDK 或第三方协议错误，按第 2.2 节转换并保留 cause，附加依赖名和操作上下文。不能机械透传第三方状态码：服务自身调用第三方的凭证失效属于依赖故障，不等于当前客户端应收到 401。HTTP 出口按第 4.1 节转换调用结果。

引入依赖时明确其初始化失败是否阻止启动，以及运行时是否允许降级。默认不吞错返回成功或将查询失败解释为空数据。

默认不增加应用层自动重试。实际需要时明确可重试错误、最大尝试次数、退避策略及幂等前提；参数错误、认证失败、业务拒绝不盲目重试。写操作超时且结果未知时，先依赖幂等机制、结果查询或明确的恢复策略，不能直接重复写入。

检查 SDK 自带重试，避免多层叠加；重试和退避共用第 3.3.2 节总预算，取消或期限耗尽立即停止。

交互日志按第 3.3.3 节记录每次尝试，中间失败不逐次记录终结 ERROR。重试或明确降级后最终成功不记整体失败 ERROR；最终失败由统一边界记录一次，并保留尝试次数和最终原因。

## 4. HTTP 服务

本章适用于 HTTP 服务，Gin 相关规则在使用 Gin 时适用；接口与实现约定用于新项目，既有项目按第 1 章保留兼容性。

### 4.1 HTTP 契约

#### 4.1.1 错误响应与统一出口

由 `internal/httpapi/error_handler.go` 统一识别错误、构造专用响应对象并输出。沿错误链识别第 2.2 节定义的应用错误，输出以下结构，不直接序列化内部错误对象：

```json
{
  "code": 409,
  "reason": "ORDER_ALREADY_PAID",
  "message": "订单已支付，不能重复付款",
  "request_id": "<请求标识>"
}
```

`code`、`reason`、`message`、`request_id` 必须存在；非空 Metadata 使用 `metadata` 字段输出，空时省略。HTTP 状态码与正文 code 一致，不使用 HTTP 200 承载失败。调用方按状态码处理通用行为、按 reason 判断业务分支。JSON 响应使用 `application/json`，允许 charset；内部 cause、堆栈和包装上下文不进入响应。

常见状态与通用 Reason 如下；有明确业务含义时使用模块定义的 Reason，保持状态语义一致。只有实际引入相应功能时才实现对应业务和鉴权流程：

| 场景 | HTTP 状态 | 通用 Reason |
| --- | --- | --- |
| 请求参数无效 | 400 | `INVALID_ARGUMENT` |
| 缺少或无效的身份凭证 | 401 | `UNAUTHENTICATED` |
| 身份已确认但权限不足 | 403 | `PERMISSION_DENIED` |
| 路由或资源不存在 | 404 | `NOT_FOUND` |
| 方法不支持 | 405 | `METHOD_NOT_ALLOWED` |
| 资源状态冲突 | 409 | `CONFLICT` |
| 请求体超过接口允许大小 | 413 | `PAYLOAD_TOO_LARGE` |
| 请求体媒体类型不受支持 | 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 请求受限流策略拒绝 | 429 | `TOO_MANY_REQUESTS` |
| 未识别错误、非预期内部故障或响应前 panic | 500 | `INTERNAL_ERROR` |
| 已识别的依赖不可用、服务端操作或依赖超时 | 503 | `SERVICE_UNAVAILABLE` |

有效且明确构造的应用错误保留其状态、Reason、Message 和 Metadata。普通错误中识别出的超时或依赖不可用使用 503 通用错误；其余统一使用 `500 / INTERNAL_ERROR` 和固定文案，例如“服务内部错误”。

无效应用错误（如状态不属于 4xx/5xx、Reason 或 Message 为空）同样按内部故障兜底，保留内部诊断。客户端取消和内部取消优先按第 4.1.4 节判定，不能把它们一律映射成超时。

#### 4.1.2 请求解码与参数校验

按“请求解码 → 参数校验 → 业务校验”处理。HTTP 边界负责格式、类型、必填、范围及不依赖外部状态的字段组合校验；查询数据状态、权限归属等业务校验由业务模块负责，业务不变量不能只依赖 HTTP 校验。解码或参数校验失败返回 `400 / INVALID_ARGUMENT`；业务校验返回其模块定义的状态和 Reason。失败后不执行后续业务操作。

Gin 服务复用其 `go-playground/validator/v10` 校验能力，使用 `binding` 标签声明常见规则，复杂字段组合使用结构级或显式校验。依赖按第 5.1 节固定版本。

自定义规则和字段名映射在启动时注册并检查错误，处理请求期间不修改校验器。校验器配置错误、错误的调用类型（如 `validator.InvalidValidationError`）属于服务内部故障。

使用返回错误而不自动提交响应的绑定方式，如适用的 `ShouldBind*`，避免 `Bind*`/`MustBind*` 提前写入响应。JSON 使用统一解码辅助函数落实严格解码，再调用复用的校验器，避免重复校验；不能假定默认 `ShouldBindJSON` 已满足全部要求：

- 请求体只接受一个符合接口类型的 JSON 值；首个值之后再次解码必须得到 EOF，拒绝第二个 JSON 值或尾随垃圾。
- 对结构化请求拒绝未知字段，接口明确声明的开放字典除外。JSON 类型严格匹配，不将字符串 `"123"` 隐式转换成数字；query/path/header 的字符串按声明类型解析。
- 必需请求体为空时返回参数错误。字段是否必填、是否允许 null、零值或空字符串由接口契约声明；需要区分缺失与 null 时使用存在性标记或适当类型，不能仅靠普通指针或 validator 的 `required` 标签推断全部语义，也不能把合法的 `0`、`false` 当作未提供。
- 不隐式修剪、改写或规范化输入，除非接口明确约定。长度规则说明按字节、Unicode 码点还是其他单位计算，并与实现保持一致。
- 校验接口支持的 Content-Type；不支持的媒体类型和请求体超限使用第 4.1.1 节对应的 415、413。读取失败必须分类，客户端取消、超时及其他 I/O 故障按既有结果规则处理，不一律返回 400。

每次返回一个错误：解码失败不继续校验，参数校验采用明确且稳定的字段和规则顺序，不能依赖 map 遍历顺序或盲取校验库返回列表第一项。需要遍历字典或汇总库错误时，先按约定顺序确定首个错误。首个错误不代表请求只有一处错误。

在 HTTP 层集中将解码错误、validator 字段错误及显式参数校验错误转换为应用错误，业务特有规则由所属请求的校验逻辑定义。Message 按错误类别提供可读说明。Metadata 按以下接口契约生成，所有值为字符串：

| 键 | 约定 |
| --- | --- |
| `location` | 参数来源：`body`、`query`、`path`、`header` |
| `field` | 能可靠定位时提供对外字段路径，例如 `quantity`、`items[0].quantity`；body 使用 JSON 名称，其他来源使用接口参数名 |
| `rule` | 稳定类别：`syntax`、`unknown_field`、`required`、`type`、`format`、`range`、`length`；特殊组合规则扩展时同步接口文档 |
| `min`、`max` | range 错误中适用的数值边界 |
| `min_length`、`max_length` | length 错误中适用的长度边界，单位遵循字段契约 |

| 示例 | Message | Metadata |
| --- | --- | --- |
| quantity 超出 1–100 | 购买数量必须在 1 到 100 之间 | `location=body`、`field=quantity`、`rule=range`、`min=1`、`max=100` |
| JSON 语法错误 | 请求体不是有效的 JSON | `location=body`、`rule=syntax`；无法定位字段时省略 `field` |

未知字段使用 `unknown_field`，必需请求体缺失使用 `required`。

#### 4.1.3 请求关联与路由边界

响应头 `X-Request-ID` 与 JSON 正文的 `request_id` 一致。请求 ID 接受 1–128 位 `[A-Za-z0-9._-]`；缺失或非法时使用 `crypto/rand.Read` 生成 16 字节、编码为 32 位十六进制。按所选 Go API 的实际语义处理生成结果。请求 ID 只用于关联，不用于认证或幂等判断。

正式路由包含实际业务功能及明确声明的运维端点（如第 4.4 节的 `/metrics`），不暴露故障、panic 或延时调试接口。

#### 4.1.4 取消与响应完成状态

| 情形 | 处理与记录 |
| --- | --- |
| 客户端取消原始请求，当前错误确由该取消引起 | 停止工作，不补写成功或错误响应；记录 `outcome=canceled`，取消本身不记 ERROR |
| 内部子操作取消，原始请求仍有效 | 按非预期内部失败处理，不能当作客户端取消 |
| 服务端操作期限或依赖超时 | 响应未写时返回约定的 503 错误，记录一次 ERROR |
| 预期业务拒绝或 404/405 | 返回约定结果，不自动记 ERROR |
| 非预期失败或 panic | 记录一次 ERROR；未写响应时返回错误；已提交响应时中断尚未完成的连接或流，不追加 JSON |

判断客户端取消时使用传输层原始请求上下文，不能拿内部派生上下文的取消替代，也不能仅凭 `context.Canceled` 判断。客户端取消同时出现独立故障时，仍需保留该故障记录。最终结果由第 4.2 节的统一边界记录。

### 4.2 中间件与请求完成边界

使用 `gin.New()`，显式安装请求 ID、结果记录和恢复中间件；关闭调试输出，生产使用 release 模式。禁用默认可信代理，检查 `SetTrustedProxies(nil)` 的返回错误；有反向代理要求时再配置可信网段。

请求 ID 在处理前可用；恢复中间件捕获处理器 panic，确定结果后交给统一完成边界记录。避免叠加同责日志或恢复中间件，保留 `http.ErrAbortHandler` 的中断语义。

日志与指标共用一个完成边界：进入应用处理链时开始单调计时并增加在途计数，退出时记录最终结果、减少在途计数。每个纳入指标统计的请求只增加一次请求计数、观察一次耗时，覆盖成功、拒绝、失败、超时、取消和 panic。日志级别不影响指标采集。

耗时指应用处理时长，不以收到响应头为完成点，也不代表客户端已收到全部数据。日志使用毫秒，指标使用秒。最终结果字段按下表确定：

| 字段 | 取值 |
| --- | --- |
| `route` | 路由模板；未匹配时为 `unmatched` |
| `method` | 请求方法；指标标签使用固定方法集合，未知方法归为 `OTHER` |
| `status` | 实际已提交状态；未提交时为 `none` |
| `outcome` | `success/rejected/failure/timeout/canceled`，分别表示成功、预期拒绝、非预期失败、超时、客户端取消；按第 4.1.4 节判定 |

响应提交后失败或 panic 时保留实际状态码，同时记录失败结果。指标纳入范围见第 4.4 节。

### 4.3 启动与关闭

由 `http.Server` 承载 Gin，监听地址、各阶段超时及关闭期限使用第 3.1 节加载后的配置。

采用 `main → run → error`：`run` 负责运行与清理，`main` 负责最终失败日志和退出码。监听失败立即返回；不要用 `router.Run()` 代替生命周期管理。

收到 SIGINT/SIGTERM 后，使用独立、受 `shutdown.timeout` 限制的上下文执行 `Shutdown`，允许在途请求完成。超时则调用 `Close` 并返回关闭失败，等待 `Serve` 所在的 goroutine 退出。关闭操作不使用已取消的信号上下文。正常 `http.ErrServerClosed` 不记 ERROR。

### 4.4 运行指标与告警

使用 `github.com/prometheus/client_golang`，按第 5.1 节固定依赖版本。独立构造并注入 Registry，明确处理注册错误，避免全局注册状态和重复注册。提供以下基础指标：

| 指标 | 类型与含义 |
| --- | --- |
| `http_server_requests_total` | Counter，处理结束时计数，用于计算流量、失败率及取消比例 |
| `http_server_request_duration_seconds` | Histogram，以秒记录应用处理耗时，用于观察分布及计算 P95/P99 |
| `http_server_requests_in_flight` | Gauge，进入处理链递增，实际退出时递减；不使用尚未确定的结果标签 |
| Go 运行时与进程指标 | 注册库提供的 Go 和进程采集器，观察内存、GC、goroutine 及支持的平台进程指标 |

请求计数和耗时使用第 4.2 节定义的 `route`、`method`、`status`、`outcome` 作为有限维度标签。

指标标签不得使用请求 ID、用户 ID、订单 ID、任意错误文本、动态业务标识或带参数的完整 URL。Histogram 桶边界在构造时固定，覆盖项目关心的延迟范围，不随请求生成；各实例保持兼容的桶定义，README 记录指标名称、单位、标签及桶配置。

内部失败率结合 `outcome` 计算，客户端取消和预期业务拒绝单独统计。

通过 `GET /metrics` 暴露 Registry，使用库的 promhttp Handler 输出标准指标格式，不套用业务 JSON 响应和错误包装。该采集端点排除在上述应用 HTTP 请求指标之外，避免采集流量干扰业务指标；其他应用路由默认纳入统计。部署访问方式见第 5.3 节。第三方调用使用第 3.3.3 节日志；需要指标时按依赖名和操作名扩展。

生产项目在 README 或所引用的运维文档中说明如何发现服务不可访问、错误率持续升高及耗时持续恶化，并记录告警窗口、阈值、通知去向和排查步骤。阈值按项目目标确定；比例告警同时考虑最小请求量，避免低流量误报。区分采集失败与业务不可访问，不能仅凭 `/metrics` 可抓取就认定业务正常。初始化不要求部署整套监控系统，实际接入后验证采集、告警触发与恢复。

## 5. 初始化与部署

### 5.1 确认输入与版本

模块路径依次取用户指定值、仓库地址、`example.com/<规范化的项目目录名>`。使用默认路径时在交付中说明。

无已有版本约束时使用以下基线；Gin 仅在选择 Gin 构建 HTTP 服务时引入：

| 项目 | 初始化基线 |
| --- | --- |
| Go | `1.27.3` |
| Gin | `v1.12.0` |
| Staticcheck | `v0.8.2` |

Go 版本要求只维护在 `go.mod`：`go` 指令声明最低版本，`toolchain` 指令可指定建议工具链。新项目采用上表基线；Makefile 和 README 引用项目要求，不另设版本限制。版本变更时核实代码、依赖与工具的兼容性。

检查 Go 是否可用，不擅自更换系统工具链；遵循环境的 `GOTOOLCHAIN` 设置。自动选择可能下载工具链；设置为 `local` 且版本不足时明确失败。依赖与检查工具固定具体版本，不使用 `@latest`；检查工具版本维护在 Makefile。

### 5.2 创建文件与划分职责

将 Makefile 中 `SERVICE ?= service` 的占位值替换为主要服务名，例如 `orders`；名称使用小写字母、数字和连字符，以字母开头。入口按第 2.1 节组织，构建与运行方式见第 6.2 节。

| 路径 | 职责 |
| --- | --- |
| `cmd/<service>/main.go` | 配置读取、依赖组装、启动与关闭 |
| `cmd/<service>/main_test.go` | 程序运行与退出测试；HTTP 服务覆盖监听与关闭 |
| `configs/config.yaml` | 唯一默认配置，开发、测试、生产共用，随程序或镜像交付 |
| `.env.example` | `make dev` 的开发环境变量示例；复制为 `.env` 后按需修改，实际 `.env` 不入库 |
| `internal/config/` | 强类型配置、文件加载、环境变量覆盖、校验及测试 |
| `internal/apperror/error.go`、`error_test.go` | 第 2.2 节的通用错误能力；具体业务错误随所属模块添加 |
| `internal/httpapi/` | 使用 HTTP/Gin 时放置路由、请求解码与校验、适配、结果记录与指标集成及其测试；`error_handler.go` 负责统一错误出口 |
| `go.mod`、`go.sum` | 单模块及固定依赖 |
| `Makefile` | 复制本技能同目录模板，作为工程执行入口 |
| `Dockerfile`、`compose.yaml`、`.dockerignore` | 服务项目按第 5.3 节构建和部署 |
| `.agents/skills/scratch-go/` | 保存本手册及 Makefile 模板，供项目内持续引用 |
| `AGENTS.md` | 后续开发约束入口 |
| `README.md` | 环境、版本、配置、接口与 Makefile 目标说明 |
| `.gitignore` | 忽略 `/bin/`、`/.tools/`、`/coverage.out`、`/.env` 和其他本地秘密文件；保留 `go.sum`、`.env.example` |

只创建实际需要的业务模块、数据访问代码和基础设施配置。保留已有项目路径时，同步调整 Makefile 和 Dockerfile 构建入口。

从全局技能初始化时，将当前 `SKILL.md` 和 `Makefile` 复制到项目的技能目录；已在目标目录时不重复复制。工程根 Makefile 是实际配置，技能内的 Makefile 只作模板，后续不自动覆盖根文件。

在根 `AGENTS.md` 中加入以下内容；已有文件只合并该约定，不重写其他指令：

README 汇总服务名、Makefile 用法，并提供配置、开发环境、部署、指标与告警的文档入口，具体内容按对应章节维护；工程规范引用本手册。接口文档记录实际业务 Reason、状态码及 Metadata 契约，通用错误响应格式引用第 4.1 节。

新建 HTTP 服务时，按第 4 章实现并增加 `GET /api/v1/ping`，返回 HTTP 200 和 `{"message":"pong","request_id":"<请求标识>"}`，作为初始可用性验证。

### 5.3 Docker Compose 部署

本节适用于服务项目。根目录提供 `Dockerfile`、`compose.yaml` 和 `.dockerignore`，开发、测试和生产共用，使用 Docker Compose v2。默认从已确认版本的源码执行 `docker compose up -d --build` 完成单机部署；已有发布流程继续沿用。

#### 5.3.1 镜像构建

Dockerfile 使用多阶段构建，构建主要服务入口并注入可追溯的 `version`。构建镜像固定版本并满足 `go.mod` 的要求，不另设语言最低版本；服务名和版本与 Makefile 的 `SERVICE`、`VERSION` 语义一致。

运行镜像固定版本，仅携带程序、同一份 `configs/config.yaml` 和必要的 CA 证书、动态库等运行依赖。无 CGO 依赖时可以静态构建，有 CGO 依赖时选择匹配的运行镜像。以非 root 用户运行，确认配置可读；使用 exec 形式的 ENTRYPOINT 直接启动程序，使 SIGTERM 能到达应用。

`.dockerignore` 排除 Git 数据、本地构建产物、工具缓存、`.env` 及其他秘密文件，保留 `configs/config.yaml` 和构建所需源码；秘密不得通过 Dockerfile、构建参数或镜像层交付。

#### 5.3.2 环境变量与网络

Compose 显式列出允许传入容器的应用环境变量，使用无值透传形式，例如 `environment: [HTTP_ADDR, LOG_LEVEL]`。宿主机未设置的变量应在容器中保持未设置，由 YAML 默认配置决定；显式空值必须保留给应用校验。不要使用 `${VAR:-默认值}` 重复应用默认值，也不要将未设置变量转换为空字符串。新增配置映射时同步 Compose 和 README。

可用 `LOG_LEVEL=warn docker compose up -d --build` 覆盖；如操作者使用 Compose 的 `.env` 或 `--env-file`，它们只是部署工具的变量来源，仍需通过 `environment` 显式传入容器，真实值文件不入库。

Compose 仅声明实际需要的服务、端口、卷和依赖，不预置数据库或 Redis。HTTP 容器端口映射须与实际监听地址一致；若覆盖 `HTTP_ADDR`，同步容器目标端口。生产通过反向代理提供公网入口时，宿主机端口绑定回环地址或使用容器内部网络，README 说明实际暴露方式。

HTTP 服务按第 4.4 节提供 `/metrics`，Compose 网络或代理配置明确采集方如何访问及允许的访问范围，README 记录采集地址。默认不额外创建 Prometheus、Grafana 容器；实际接入已有监控系统或决定自建后再配置采集与告警。

#### 5.3.3 运行与更新

常驻服务使用 `restart: unless-stopped`，日志输出 stdout/stderr，并设置日志轮转，例如 `json-file` 的 `max-size: 10m`、`max-file: 3`。`stop_grace_period` 默认 `15s`，必须大于应用关闭期限；覆盖 `SHUTDOWN_TIMEOUT` 时同步检查。

README 说明构建、启动、查看日志、停止及更新命令。配置环境变量改变后通过 `docker compose up -d` 重建受影响容器，单独 `restart` 不会更新容器环境。

生产更新保留上一版本源码或镜像及对应环境配置，以便回滚；涉及数据迁移时单独说明兼容性。单副本 Compose 更新允许短暂中断，不承诺零停机。

## 6. 验证与交付

### 6.1 测试真实行为

测试覆盖实际功能的正常、失败和资源清理路径；修复缺陷时增加能重现问题的回归测试。CLI 和 Worker 验证输入、输出、退出状态、取消及资源回收等适用行为。

#### 6.1.1 配置与应用错误

配置测试调用生产加载逻辑，覆盖仓库默认文件可加载、环境变量优先级、未设置与空值的区别、显式零值/false、非法类型/时长、未知字段、缺失文件、必填项等适用行为。使用临时文件构造错误配置，默认文件路径由入口固定传入，测试不修改仓库配置。

测试通过可注入的环境查询函数隔离输入；使用 `t.Setenv` 时不得并行执行或从并行父测试调用，避免污染其他测试。验证无效配置在监听和外部依赖初始化前失败。

应用错误测试覆盖 `%w` 包装后的 Is/As 判断、相同 Code + Reason 的匹配及不同状态或业务码的不匹配、Unwrap 原因保留、附加原因和元数据不修改原对象，以及传入或读出元数据的修改不影响错误。业务错误测试检查构造函数的状态与稳定 Reason，HTTP 响应测试验证响应字段与约定一致。

#### 6.1.2 外部依赖

实际引入外部依赖时，使用可控替身或本地测试服务调用生产适配逻辑，验证以下行为，不依赖真实第三方在线服务：

| 验证项 | 断言 |
| --- | --- |
| 期限与取消 | 较短的上游期限生效，实际配置的阶段超时生效，响应头已到达后慢响应体仍受总期限控制，读取完成前上下文未被提前取消 |
| 重试与错误转换 | 按实际启用策略验证次数、退避取消和总预算，不重试不满足条件的写操作；第三方认证错误不误报为客户端 401，错误链及最终失败日志符合约定 |
| 日志级别与数量 | DEBUG 每次尝试两条交互事件，普通文本完整记录且无 INFO 摘要；INFO 每次尝试一条摘要；WARN/ERROR 不捕获常规报文，重试可通过 call_id 和 attempt 关联 |
| 截断与完成状态 | 覆盖 1024 字符边界及多字节字符，请求和响应分别截断，摘要不完整缓存报文；无响应、部分响应、取消、读取/解析失败均只有一次完成事件，status/outcome/response_complete 正确 |
| 资源与读写语义 | 请求内容不变、响应体仍可由业务完整读取，Close 和取消有效；文件和流式内容不被日志预读或整体缓冲；成功、失败、启动中途失败及停机均释放所持资源 |

#### 6.1.3 HTTP 服务

HTTP/Gin 服务的测试使用实际路由构造器、中间件和错误出口，只在底层依赖或叶子处理器处注入行为。不要另写一套测试中间件，也不要用测试中自行包装错误的断言代替生产错误链验证。没有业务传播链时仅验证现有边界，待实际引入调用链后补测。

HTTP 服务按实际契约验证以下适用行为：

| 必测行为 | 断言 |
| --- | --- |
| 实际接口（新建服务为 ping）与请求 ID | 状态、完整 JSON 结构、Content-Type、头/体 ID；合法 ID 保留，非法或缺失 ID 替换 |
| 请求解码 | 覆盖无效 JSON、类型错误、未知字段、尾随内容、必需请求体为空，以及实际支持的媒体类型和体积限制；按契约返回 400/413/415，不能提前写入其他响应或把取消、I/O 故障误报为参数错误 |
| 参数校验 | 覆盖实际字段的必填、边界、格式和组合规则；区分缺失/null/零值，验证允许的 0/false 可通过；多个错误时首个错误稳定，状态、Reason、Message 和 Metadata 符合第 4.1.2 节，业务操作未被调用 |
| 校验故障与业务边界 | 校验器配置/调用故障按内部错误处理并保留诊断；业务规则仍经业务入口验证 |
| 业务及通用 4xx | 通过实际出口断言状态与 code 一致、reason/message 正确、metadata 有值时输出且空时省略、请求 ID 头体一致；覆盖实际存在的业务拒绝及 404/405，不产生故障 ERROR |
| 未识别的普通错误及无效应用错误 | 统一兜底为 500 和约定的 INTERNAL_ERROR 响应；生产边界只记一次终结 ERROR，保留诊断和关联信息 |
| 显式应用错误和包装传播 | 包装后仍返回约定的响应字段，cause 不进入响应；最终 5xx 记一次 ERROR，不因自定义类型而忽略故障 |
| 取消、超时与依赖不可用 | 分别覆盖客户端取消、请求有效但内部子操作取消、服务端超时及已识别的依赖不可用；后两者按约定返回 503，核对响应及日志，内部失败不得得到默认 200 |
| panic | 响应前返回 500；日志含路由和实际处理器的堆栈位置；后续请求仍可处理 |
| 响应后的 panic | 在响应头已发送、正文未完成时注入 panic，通过真实本地 HTTP 连接确认中断；不追加 JSON、不误记成功，不能只用 ResponseRecorder 证明连接行为 |
| 生命周期 | 调用生产运行逻辑：监听失败返回、正常关闭无 ERROR、在途请求可完成、超时强制退出并回收资源 |

使用 `httptest` 和本地临时监听地址 `127.0.0.1:0`，测试自行启动和关闭服务，不依赖外部运行实例。通过可注入停止信号测试生命周期，使用同步条件和有界超时，不用 sleep 猜测时序。上述测试纳入普通测试集，不因缺少外部 URL 而跳过。

#### 6.1.4 运行指标

使用生产中间件和独立 Registry 验证正常、拒绝、失败、取消、超时及 panic 路径：Counter 和 Histogram 的观察次数只增加一次；日志含非负 duration_ms，Histogram 使用秒，两者统计范围一致。用同步控制的在途请求验证 Gauge 在处理期间递增、结束后归零，包含异常路径；响应提交后失败的实际 status 与 outcome 保持一致。

访问同一路由的不同资源 ID、随机不存在路径和未知方法，确认标签归一化且时间序列数量不随动态输入增长。请求 `/metrics` 能获取库的标准指标格式和已注册采集器，采集本身不增加应用请求指标；反复构造、关闭测试服务不发生重复注册。以上验证不要求外部 Prometheus 或 Grafana 实例，实际部署告警的验证按第 4.4 节执行。

### 6.2 检查命令

命令实现集中维护在项目 Makefile。使用 GNU Make 和 POSIX shell，从工程根目录运行以下六个入口，默认目标为 `check`：

| 目标 | 用途 |
| --- | --- |
| `make build` | 构建 `cmd/$(SERVICE)` 到 `bin/$(SERVICE)`；发布时指定可追溯的 `VERSION` |
| `make run` | 构建并前台运行所选服务 |
| `make dev` | 构建后加载根目录 `.env` 并前台运行所选服务；加载规则见第 3.2 节 |
| `make test` | 运行整个模块的行为测试，不使用测试结果缓存 |
| `make check` | 检查格式、模块一致性、编译、vet、Staticcheck，并执行整个模块的竞态测试 |
| `make fmt` | 修复 Go 源码格式 |

`build`、`run`、`dev` 默认选择 `SERVICE` 指定的服务，可用 `make build SERVICE=orders-worker`、`make run SERVICE=orders-worker` 或 `make dev SERVICE=orders-worker` 切换。`dev` 使用 exec 启动程序，保留退出状态和信号处理语义；其他目标不加载 `.env`。

`check` 自动安装并复用固定版本 Staticcheck，缓存于 `.tools`，按所选 Go 工具链版本隔离；首次安装需要网络。竞态测试需要支持的平台与 C 编译器。`check` 不修改源码或模块文件。

### 6.3 验证流程与交付记录

初始化必须通过 `check`、`build`，并验证运行中的程序行为；HTTP 服务使用实际功能请求。后续变更执行相关检查，错误、日志或并发改动需补充反例测试。`check` 已包含测试，无需为同次验收再运行 `test`。漏洞扫描由项目发布流程另行配置。

服务初始化及配置或部署变更还需执行 `docker compose config --quiet`、镜像构建和容器运行验证。使用独立 Compose 项目名及可用本地端口，验证镜像内默认配置存在、非 root 运行、环境变量未设置时保留默认值、有效覆盖生效、非法覆盖导致启动失败，以及 SIGTERM 能在宽限期内正常关闭。HTTP 服务请求实际接口（初始为 ping）；仅容器处于运行状态不算可用性通过。

失败场景临时关闭自动重启，便于核对退出码；检查结束清理本次启动的容器和网络，不影响已有部署。

缺少工具或环境能力时明确失败，交付标明未执行项，不绕过或降级检查。记录源码及工具版本、执行命令、实际结果、运行入口和必要偏离；人工复核职责边界、抽象必要性及日志的诊断价值。
