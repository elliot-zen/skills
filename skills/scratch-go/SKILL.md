# Go 后端工程开发指南

## 1. 适用范围与工作流程

本手册适用于 Go 服务、后台任务程序（Worker）和命令行程序（CLI）。通用工程规范持续适用；HTTP、外部依赖和部署要求按项目实际能力适用。

“必须”“不得”表示硬性要求；未加限定的规范性陈述同样需要落实。“默认”表示无既有约定或业务特例时采用的方案；调整时说明原因，并同步契约与测试。“例如”仅用于说明，不要求创建示例中的业务或依赖。

开始工作前读取项目的 `AGENTS.md`、相关源码、测试、依赖与 Makefile，确认现有契约、版本及用户修改。既有约定优先，保留已有文件和用户修改，仅合并当前任务所需能力。调整约定时明确影响，并同步实现、测试和文档。

| 任务 | 阅读与执行顺序 |
| --- | --- |
| 开发、修复与重构 | 第 2 章通用规范 → 第 3、4 章相关能力 → 第 6 章验证 |
| 新项目初始化 | 第 5.1、5.2 节确定版本与文件 → 第 2–4 章实现适用能力 → 服务项目按第 5.3 节部署 → 第 6 章验证 |

| 代码审查 | 依据适用章节检查真实行为、兼容性及验证证据 |

## 2. 通用工程规范

### 2.1 组织、依赖与表达

按职责和内聚性组织包；每个可执行程序的入口位于 `cmd/<command>/`，内部实现在 `internal/`。服务程序按服务名命名，例如 `cmd/orders/`；Worker 或工具按职责命名，例如 `cmd/orders-worker/`、`cmd/migrate/`。每个入口都是独立的 `package main`，仅在需要独立程序时增加目录。

业务规则不依赖 `*gin.Context` 或数据库驱动细节，按实际职责划分模块，不强制固定分层架构。

显式构造依赖，避免可变全局状态和万能 `common/utils/base` 包。默认使用具体类型；真实调用方需要隔离或替换行为时，在使用方声明最小接口。只导出实际需要的标识符。

遵循 Go 命名与格式惯例，保持函数职责清晰，不采用机械行数门槛。人工编写的源码注释使用英文，仅说明必要的公开契约、设计原因、不变量及关键限制。

### 2.2 错误分类与传播

#### 2.2.1 错误模型与定义归属

业务函数返回标准 `error`。在 `internal/apperror/error.go` 中定义轻量的 `errorForUser`，私有字段 `code`、`msg` 分别保存 HTTP 错误状态和默认公开提示，`Error()` 返回 msg。按实际需要定义共享分类值，如 `ErrInvalidArgument`（400）、`ErrPermissionDenied`（403）、`ErrNotExist`（404）、`ErrAlreadyExist`（409）、`ErrUnprocessableContent`（422）。

提供 `ErrorWrap(unwrap error, message string, args ...any)`：创建保存公开文案和被包装错误的实例，`Error()` 只返回该文案，`Unwrap()` 返回被包装错误。按需提供 `NewInvalidArgumentErrorf`、`NewPermissionDeniedErrorf`、`NewNotExistErrorf`、`NewAlreadyExistErrorf` 等便捷函数，固定分类并调用 ErrorWrap。

业务模块在自己的 `errors.go` 中定义业务哨兵错误或具体错误类型。只需判断身份时使用哨兵错误；需要携带业务信息时使用结构体并实现 `Error()`，可通过 `Unwrap()` 归入上述公开分类。凡可解包到公开分类的错误，其最外层 `Error()` 文本必须可安全返回给用户。普通技术故障保留原始错误及操作上下文，不包装为公开业务拒绝。

使用 `errors.Is` 判断哨兵或分类，使用 `errors.As` 提取具体错误；确需 `IsXxx(err)` 辅助函数时内部也使用 Is/As，支持包装后的错误，不依赖直接类型断言或错误字符串。

提供 `ErrorUnwrapForUser(err) (message string, status int)`，沿错误链查找 errorForUser，找到时返回最外层 `err.Error()` 和分类状态，未找到时返回空文案和 0。错误类型不依赖 Gin；共享分类不保存请求数据，包装实例按次创建，不强制统一的 AppError 结构。

参考实现：[Gitea 错误分类与包装](https://github.com/go-gitea/gitea/blob/main/modules/util/error.go)、[业务错误类型](https://github.com/go-gitea/gitea/blob/main/models/repo/repo.go)。

#### 2.2.2 传播、转换与最终处理

常规失败返回 `error`，不使用 panic；不无理由忽略错误。技术故障在需要补充诊断信息的边界使用 `fmt.Errorf("query user level: %w", err)`，没有新信息时直接返回。公开业务错误直接传播或使用安全文案包装；不得在其外层追加 SQL、凭证或其他内部上下文。

仅在语义明确的边界转换技术错误：确认记录不存在才能转为业务未找到，确认特定唯一约束冲突才能转为相应业务冲突；数据库断连等技术故障不能转换为业务拒绝。业务层返回 error，HTTP 层按第 4.1 节统一输出，不由各处理器各自拼接错误响应。

错误记录遵守 [日志规范](references/logging-spec.md)，HTTP 的取消与响应提交语义见第 4.2.1 节，外部依赖的重试与降级见第 3.3 节。

### 2.3 日志与故障定位

新增、修改或审查日志、业务错误处理及 HTTP 请求记录时，阅读并遵守 [日志规范](references/logging-spec.md)。输出格式、字段、级别、故障定位、脱敏及日志测试统一维护在该文件中。

### 2.4 上下文、并发与资源

可取消操作以 `ctx context.Context` 为首参并沿调用链传递，业务层使用标准上下文。不随意用 `context.Background()` 替换请求上下文；不用上下文传递业务参数或长期保存请求上下文，也不跨请求保留 `*gin.Context`。

释放创建的取消函数；每个 goroutine 都有所有者、退出条件和等待机制，共享状态正确同步。

明确文件、响应体、连接和事务的清理责任，覆盖成功、失败与取消路径，检查有意义的 `Close`、`Commit` 错误。

**应用级关闭总时限：**HTTP 排空、后台任务退出和资源清理共用关闭总时限，各阶段不得重新计时延长总时限；超时后执行强制退出策略。

## 3. 配置与外部依赖

### 3.1 默认配置与环境变量

新项目只维护一份 `configs/config.yaml`，提交 Git，列出应用实际支持的配置项和默认值。开发、测试和生产使用同一文件，各环境仅通过环境变量覆盖。默认值集中维护在该文件，Go 代码和 Compose 不重复设置。配置从固定路径读取，作为外部文件交付。

启动顺序固定为：读取 `configs/config.yaml` → 应用环境变量覆盖 → 校验最终配置 → 组装依赖并启动。路径相对于进程工作目录；本地从项目根目录启动，容器工作目录固定为 `/app`，配置复制到 `/app/configs/config.yaml`。文件是运行所需交付物，不自动搜索其他路径，也不在文件缺失时静默使用代码默认值。

由 `internal/config` 提供强类型配置及加载、解析和校验能力，入口调用一次并将所需配置显式传给依赖。业务代码不自行读取环境变量，不使用可变全局配置。配置或环境变量变更后重启进程。

环境变量采用大写下划线命名，为每个可覆盖字段维护明确、唯一的映射；避免嵌套字段扁平化后重名。只读取声明支持的变量，不把进程中其他环境变量当作配置错误。HTTP 服务至少提供下列配置；Worker/CLI 仅保留适用项，后续依赖按实际需要增加：

| YAML 字段 | 环境变量 | 默认值 |
| --- | --- | --- |
| `http.addr` | `HTTP_ADDR` | `:8080` |
| `shutdown.timeout` | `SHUTDOWN_TIMEOUT` | `10s` |
| `log.level` | `LOG_LEVEL` | `info` |

配置解析与校验遵守以下规则：

- 严格解析 YAML，拒绝未知字段、重复键、类型错误和多份 YAML 文档。使用固定版本的解析依赖，明确解析时长的行为。
- 使用 `os.LookupEnv` 区分未设置和设置为空。未设置保留文件值；显式空字符串、`false`、`0` 都参与覆盖，再按字段约束校验，不能按零值判断是否提供配置。
- 时长使用 `5s`、`1m` 等 Go duration 格式，布尔值和数值按声明类型解析。关闭期限要求大于零。
- 文件缺失或格式错误、环境变量解析失败、最终配置缺少必填项或不满足范围和跨字段约束时，启动失败并返回非零退出码，不静默回退。日志级别限定为 `debug/info/warn/error`，监听地址按服务要求校验。
- 密码、令牌等不保存真实默认值，由环境变量注入；依赖启用时校验对应秘密必填。诊断指出字段或环境变量名称及来源。

README 维护字段、环境变量、用途、默认值及约束清单。

### 3.2 开发环境

应用不自动加载 `.env`。开发入口 `make dev` 在构建后通过 POSIX shell 读取项目根目录的 `.env`，将变量导出给前台运行的程序。文件不存在时使用继承的环境变量和 YAML 配置，读取或执行失败时不启动程序。

`.env` 中的同名赋值覆盖继承的环境变量，未赋值的变量保留原值。需要直接使用命令行环境覆盖时运行 `make run`，例如 `HTTP_ADDR=:8081 LOG_LEVEL=debug make run`；该目标不读取 `.env`。README 提供两种启动方式的示例。

`.env` 是通过 shell 的 `.` 加载的可信本地文件，采用 `KEY=value` 赋值语法。含空格、`#` 或字面量 `$` 的值使用单引号，不写命令或命令替换；不承诺支持所有 dotenv 扩展语法。仅填写必要的开发覆盖项。

初始化时提供不含秘密的 `.env.example`，实际 `.env` 加入 `.gitignore` 和 `.dockerignore`。`.env` 在构建后加载，不负责设置 `SERVICE`、`VERSION` 或构建工具参数。

### 3.3 外部依赖调用

本节适用于实际引入的数据库、Redis、第三方 HTTP 等依赖，不预建适配层或配置。

#### 3.3.1 构造与配置

每个依赖在 `configs/config.yaml` 的 `dependencies.<name>` 下维护实际需要的配置，并按第 3.1 节提供显式环境变量映射；README 和 Compose 同步映射。

入口读取配置并构造依赖，适配层提供业务所需能力。按 SDK 契约复用并发安全的客户端和连接池，不逐请求创建 `http.Client`、`http.Transport` 或数据库连接池。

启动中途失败时清理已创建资源。关闭时先停止接收工作、等待在途任务，再关闭依赖客户端和连接池，遵守程序关闭期限。

#### 3.3.2 调用、错误与重试

调用传递调用方上下文；SDK 不支持上下文时说明取消限制。响应体、`Rows`、事务等由创建或取得资源的调用方负责结束，取消函数的生命周期覆盖响应体读取和关闭。

适配层识别 SDK 或第三方协议错误，按第 2.2 节分类并保留底层原因，附加依赖名和操作上下文。不能机械透传第三方状态码：服务自身调用第三方的凭证失效属于依赖故障，不等于当前客户端应收到 401。HTTP 出口按第 4.1 节转换调用结果。

引入依赖时明确其初始化失败是否阻止启动，以及运行时是否允许降级。默认不吞错返回成功或将查询失败解释为空数据。

默认不增加应用层自动重试。实际需要时明确可重试错误、最大尝试次数、退避策略及幂等前提；参数错误、认证失败、业务拒绝不盲目重试。写操作超时且结果未知时，先依赖幂等机制、结果查询或明确的恢复策略，不能直接重复写入。

检查 SDK 自带重试，避免多层叠加；重试和退避沿用调用方上下文，上下文结束时停止。

第三方 HTTP 交互、重试和降级的日志遵守 [日志规范第 2、4 节](references/logging-spec.md)。

### 3.4 数据库规范

新增、修改或审查数据库表结构、迁移及数据访问代码时，阅读并遵守 [数据库规范](references/database-spec.md)。

## 4. HTTP 服务

本章适用于 HTTP 服务，Gin 相关规则在使用 Gin 时适用；接口与实现约定用于新项目，既有项目按第 1 章保留兼容性。

### 4.1 API 实现

新增、修改或审查 HTTP API 时，阅读 [API 规范](references/api-spec.md)，落实命名、请求校验、响应、错误码、分页和协议例外。

#### 4.1.1 统一错误出口

由 `internal/httpapi/error_handler.go` 提供统一错误出口。先按第 4.2.1 节处理取消与响应状态，再调用 `ErrorUnwrapForUser` 提取公开文案和 HTTP 状态；未识别时按 API 规范兜底。处理器调用同一出口，不自行拼接错误响应。

业务特有的哨兵或类型由所属 HTTP 适配代码通过 `errors.Is/As` 识别，向统一出口提供状态、安全文案和业务错误码。`error_code`、`metadata` 在 HTTP 层生成；`metadata` 使用 `map[string]string`，每次响应独立构造。

#### 4.1.2 解码与校验

按“请求解码 → 参数校验 → 业务校验”处理。HTTP 层负责格式、类型、必填、范围及不依赖外部状态的字段组合校验；数据状态、权限归属等由业务模块校验，业务不变量不能只依赖 HTTP 校验。失败后停止后续业务操作。

Gin 服务复用其 `go-playground/validator/v10` 校验能力，使用 `binding` 标签声明常见规则，复杂字段组合使用结构级或显式校验。依赖按第 5.1 节固定版本。

自定义规则和字段名映射在启动时注册并检查错误，处理请求期间不修改校验器。校验器配置错误、错误的调用类型（如 `validator.InvalidValidationError`）属于服务内部故障。

使用返回错误而不自动提交响应的绑定方式，如适用的 `ShouldBind*`，避免 `Bind*`/`MustBind*` 提前写入响应。JSON 沿用所选解码器的默认行为，绑定已执行的校验不重复调用。

需要区分字段缺失与 null 时使用存在性标记或适当类型，不能仅靠普通指针或 validator 的 `required` 标签推断全部语义。

HTTP 层集中识别解码错误、validator 字段错误和显式参数校验错误，通过统一出口生成响应；跨函数传递校验信息时使用具体错误类型。业务特有规则由所属请求的校验逻辑定义，对外文案与 `metadata` 遵守 API 规范。

### 4.2 请求处理与完成边界

#### 4.2.1 结果处理

以下规则适用于尚未接管的 HTTP 连接；接管后的处理见第 4.2.3 节。

| 情形 | 处理 |
| --- | --- |
| 客户端取消原始请求，当前错误确由该取消引起 | 标记取消，停止工作，通过 `panic(http.ErrAbortHandler)` 中断，不补写响应 |
| 内部子操作取消，原始请求仍有效 | 按非预期内部失败处理，不能当作客户端取消 |
| 超时或依赖故障 | 响应未提交且连接仍可写时返回 `500 / INTERNAL_ERROR`；否则中断 |
| 预期业务拒绝或 404/405 | 返回约定结果 |
| 非预期失败或 panic | 未提交响应时返回 500；已提交响应时通过 `http.ErrAbortHandler` 中断尚未完成的连接或流，不追加 JSON |

判断客户端取消时使用传输层原始请求上下文，不能拿内部派生上下文的取消替代，也不能仅凭 `context.Canceled` 判断。仅 `return` 或 `c.Abort()` 不能阻止 Gin 提交默认响应。`http.ErrAbortHandler` 仅用于传输中断，不作为业务 panic；中断前保存取消或故障结果，同时发生的独立故障不能被取消覆盖。最终结果交给统一完成边界记录，日志遵守 [日志规范](references/logging-spec.md)。

#### 4.2.2 路由与中间件

使用 `gin.New()`，设置 `RedirectTrailingSlash=false`、`RedirectFixedPath=false`，路径不匹配交给统一 404 出口；启用 `HandleMethodNotAllowed`，通过 `NoRoute`、`NoMethod` 输出统一 404/405，405 保留 `Allow` 头。关闭调试输出，生产使用 release 模式。禁用默认可信代理，检查 `SetTrustedProxies(nil)` 的返回错误；有反向代理要求时再配置可信网段。

正式路由包含实际业务功能及明确声明的运维端点（如第 4.4 节的 `/metrics`），不暴露故障、panic 或延时调试接口。

请求 ID 接受 1–128 位 `[A-Za-z0-9._-]`；缺失或非法时使用 `crypto/rand.Read` 生成 16 字节、编码为 32 位十六进制。按所选 Go API 的实际语义处理生成结果。请求 ID 只用于关联，不用于认证或幂等判断。

在 Gin `ServeHTTP` 外层设置统一 HTTP 包装器，负责请求 ID、响应状态跟踪、恢复及完成记录。进入 Gin 前将请求 ID 和本次请求的结果状态放入标准上下文；Gin 适配代码在上下文回收前保存路由模板和解析后的客户端地址，错误出口保存故障结果。外层不持有 `*gin.Context`，响应记录器保留底层流式与连接控制能力。

正常返回时，先让 Gin 完成响应提交，再记录，包括仅设置 204 等状态的无正文响应。恢复层按第 4.2.1 节处理普通 panic，500 复用统一响应构造逻辑；`http.ErrAbortHandler` 原样继续抛出，由 `net/http` 中断连接或流，外层 defer 仍执行完成记录。Gin 内不再安装同责的日志或恢复中间件。

普通 HTTP 请求的日志与指标共用处理链退出边界：进入时开始单调计时并增加在途计数，退出并确定最终提交或中断结果后记录并减少在途计数。每个纳入统计的请求只计数、观察耗时一次，覆盖成功、拒绝、失败、超时、取消和 panic；日志级别不影响指标采集。

普通 HTTP 的耗时指应用处理时长，不以收到响应头为完成点，也不代表客户端已收到全部数据；响应提交后失败或 panic 时保留实际状态码和失败结果。完成日志遵守 [日志规范第 3 节](references/logging-spec.md#3-请求与连接日志)，指标取值与纳入范围见第 4.4 节。

#### 4.2.3 连接接管

实际使用 WebSocket 或连接接管时，记录器跟踪接管状态；接管后由协议适配层负责错误处理、panic 恢复及连接关闭，HTTP 恢复层不再写响应，也不依赖 `http.ErrAbortHandler` 关闭连接。仅复制请求 ID 等关联值，不长期保留原 HTTP 请求上下文。

协议适配层提供实际握手结果，在握手完成时结束计时、减少在途计数并记录一次 HTTP 结果。连接存续期间的故障不回写握手结果，连接日志遵守 [日志规范第 3.2 节](references/logging-spec.md#32-连接接管与断开)。

### 4.3 启动与关闭

由 `http.Server` 承载包装后的 Gin Handler，监听地址及关闭期限使用第 3.1 节加载后的配置。

采用 `main → run → error`：`run` 负责运行与清理，`main` 负责最终失败日志和退出码。监听失败立即返回；不要用 `router.Run()` 代替生命周期管理。

收到 SIGINT/SIGTERM 后，创建独立、受 `shutdown.timeout` 限制的应用级关闭上下文，按第 2.4 节共用于 HTTP 排空、后台任务退出和资源清理；`Shutdown` 使用该上下文，允许在途请求在剩余时限内完成。超时则调用 `Close` 并返回关闭失败，等待 `Serve` 所在的 goroutine 退出；强制退出策略不得因后台任务或资源清理阻塞而无限等待。关闭操作不使用已取消的信号上下文。正常 `http.ErrServerClosed` 作为正常退出处理。

实际使用连接接管时，协议适配层管理已接管连接的生命周期。停机开始即停止接受新接管，并通知已有连接关闭，与 HTTP 排空并行执行；在同一关闭期限内等待连接清理及关闭日志完成。期限耗尽时由协议适配层强制关闭剩余连接，按上述失败退出策略结束，不继续无限等待；不能依赖 `http.Server.Shutdown` 或 `Close` 清理已接管连接。

### 4.4 运行指标与告警

使用 `github.com/prometheus/client_golang`，按第 5.1 节固定依赖版本。独立构造并注入 Registry，明确处理注册错误，避免全局注册状态和重复注册。提供以下基础指标：

| 指标 | 类型与含义 |
| --- | --- |
| `http_server_requests_total` | Counter，到达第 4.2 节规定的完成边界时计数，用于计算流量、失败率及取消比例 |
| `http_server_request_duration_seconds` | Histogram，以秒记录请求进入到第 4.2 节完成边界的单调计时，用于观察分布及计算 P95/P99 |
| `http_server_requests_in_flight` | Gauge，请求进入时递增，到达第 4.2 节规定的完成边界时递减；不使用尚未确定的结果标签 |
| Go 运行时与进程指标 | 注册库提供的 Go 和进程采集器，观察内存、GC、goroutine 及支持的平台进程指标 |

请求计数和耗时使用以下有限维度标签；这些标签不规定日志字段：

| 标签 | 取值 |
| --- | --- |
| `route` | 路由模板；未匹配时为 `unmatched` |
| `method` | 固定请求方法集合，未知方法归为 `OTHER` |
| `status` | 实际已提交状态；未提交时为 `none` |
| `outcome` | `success/rejected/failure/timeout/canceled`，分别表示成功、预期拒绝、非预期失败、超时、客户端取消；按第 4.2.1 节判定 |

普通 HTTP 响应提交后失败保留实际状态，`outcome` 反映失败；连接接管后的故障不改变已完成的握手指标。耗时单位为秒。

指标标签不得使用请求 ID、用户 ID、订单 ID、任意错误文本、动态业务标识或带参数的完整 URL。Histogram 桶边界在构造时固定，覆盖项目关心的延迟范围，不随请求生成；各实例保持兼容的桶定义，README 记录指标名称、单位、标签及桶配置。

内部失败率结合 `outcome` 计算，客户端取消和预期业务拒绝单独统计。

通过 `GET /metrics` 暴露 Registry，使用库的 promhttp Handler 输出标准指标格式，不套用业务 JSON 响应和错误包装。该采集端点排除在上述应用 HTTP 请求指标之外，避免采集流量干扰业务指标；其他应用路由默认纳入统计。部署访问方式见第 5.3 节。第三方调用日志遵守 [日志规范第 4 节](references/logging-spec.md#4-第三方-http-交互)；需要指标时按依赖名和操作名扩展。

生产项目在 README 或所引用的运维文档中说明如何发现服务不可访问、错误率持续升高及耗时持续恶化，并记录告警窗口、阈值、通知去向和排查步骤。阈值按项目目标确定；比例告警同时考虑最小请求量，避免低流量误报。区分采集失败与业务不可访问，不能仅凭 `/metrics` 可抓取就认定业务正常。初始化不要求部署整套监控系统，实际接入后验证采集、告警触发与恢复。

## 5. 初始化与部署

### 5.1 确认输入与版本

模块路径依次取用户指定值、仓库地址、`example.com/<规范化的项目目录名>`。使用默认路径时在交付中说明。

无已有版本约束时使用以下基线；Gin 仅在选择 Gin 构建 HTTP 服务时引入：

| 项目 | 初始化基线 |
| --- | --- |
| Go | `1.27.3` |
| Gin | `v1.12.0` |

Go 版本要求只维护在 `go.mod`：`go` 指令声明最低版本，`toolchain` 指令可指定建议工具链。新项目采用上表基线；Makefile 和 README 引用项目要求，不另设版本限制。版本变更时核实代码、依赖与工具的兼容性。

检查 Go 是否可用，不擅自更换系统工具链；遵循环境的 `GOTOOLCHAIN` 设置。自动选择可能下载工具链；设置为 `local` 且版本不足时明确失败。依赖固定具体版本，不使用 `@latest`。

### 5.2 创建文件与划分职责

将 Makefile 中 `SERVICE ?= service` 的占位值替换为主要服务名，例如 `orders`；名称使用小写字母、数字和连字符，以字母开头。入口按第 2.1 节组织，构建与运行方式见第 6.2 节。

| 路径 | 职责 |
| --- | --- |
| `cmd/<service>/main.go` | 配置读取、依赖组装、启动与关闭 |
| `cmd/<service>/main_test.go` | 程序运行与退出测试；HTTP 服务覆盖监听与关闭 |
| `configs/config.yaml` | 唯一默认配置，开发、测试、生产共用，随程序或镜像交付 |
| `.env.example` | `make dev` 的开发环境变量示例；复制为 `.env` 后按需修改，实际 `.env` 不入库 |
| `internal/config/` | 强类型配置、文件加载、环境变量覆盖、校验及测试 |
| `internal/apperror/error.go`、`error_test.go` | 第 2.2 节的通用错误分类及实际需要的包装能力；具体业务错误随所属模块添加 |
| `internal/httpapi/` | 使用 HTTP/Gin 时放置路由、请求解码与校验、适配、结果记录与指标集成及其测试；`error_handler.go` 负责统一错误出口 |
| `go.mod`、`go.sum` | 单模块及固定依赖 |
| `Makefile` | 复制本技能同目录模板，作为工程执行入口 |
| `Dockerfile`、`compose.yaml`、`.dockerignore` | 服务项目按第 5.3 节构建和部署 |
| `.agents/skills/scratch-go/` | 保存本手册、`references/` 下的规范及 Makefile 模板，供项目内持续引用 |
| `AGENTS.md` | 后续开发约束入口 |
| `README.md` | 环境、版本、配置、接口与 Makefile 目标说明 |
| `.gitignore` | 忽略 `/bin/`、`/coverage.out`、`/.env` 和其他本地秘密文件；保留 `go.sum`、`.env.example` |

只创建实际需要的业务模块、数据访问代码和基础设施配置。保留已有项目路径时，同步调整 Makefile 和 Dockerfile 构建入口。

从全局技能初始化时，将当前 `SKILL.md`、完整的 `references/` 目录和 `Makefile` 复制到项目的技能目录，保留相对目录结构；已在目标目录时不重复复制。工程根 Makefile 是实际配置，技能内的 Makefile 只作模板，后续不自动覆盖根文件。

在根 `AGENTS.md` 中加入以下内容；已有文件只合并该约定，不重写其他指令：

```markdown
## Go 开发约定

修改 Go 代码前，阅读 `.agents/skills/scratch-go/SKILL.md` 第 1、2、6 章；涉及配置或外部依赖时遵守第 3 章，涉及 HTTP 服务时遵守第 4 章及 `.agents/skills/scratch-go/references/api-spec.md`。
涉及数据库表结构、迁移或数据访问代码时，阅读并遵守 `.agents/skills/scratch-go/references/database-spec.md`。
初始化工程时执行第 5.1、5.2 节，服务部署遵守第 5.3 节。检查命令以工程根目录 Makefile 为准。
```

README 汇总服务名、Makefile 用法，并提供配置、开发环境、部署、指标与告警的文档入口，具体内容按对应章节维护；工程规范引用本手册。接口文档记录实际业务字段、错误码、状态码及 `metadata` 契约，对外契约引用 [API 规范](references/api-spec.md)，实现约定引用第 4.1 节。

新建 HTTP 服务时，按第 4 章实现并增加 `GET /api/v1/ping`，返回 HTTP 200 和 API 规范中的统一成功响应，`data` 为 `{"message":"pong"}`，作为初始可用性验证。

### 5.3 Docker Compose 部署

本节适用于服务项目。根目录提供 `Dockerfile`、`compose.yaml` 和 `.dockerignore`，开发、测试和生产共用，使用 Docker Compose v2。默认从已确认版本的源码执行 `docker compose up -d --build` 完成单机部署；已有发布流程继续沿用。

#### 5.3.1 镜像构建

Dockerfile 使用多阶段构建，构建主要服务入口并注入可追溯的 `version`。构建镜像固定版本并满足 `go.mod` 的要求，不另设语言最低版本；服务名和版本与 Makefile 的 `SERVICE`、`VERSION` 语义一致。

运行镜像固定版本，仅携带程序、同一份 `configs/config.yaml` 和必要的 CA 证书、动态库等运行依赖。无 CGO 依赖时可以静态构建，有 CGO 依赖时选择匹配的运行镜像。以非 root 用户运行，确认配置可读；使用 exec 形式的 ENTRYPOINT 直接启动程序，使 SIGTERM 能到达应用。

`.dockerignore` 排除 Git 数据、本地构建产物、工具缓存、`.env` 及其他秘密文件，保留 `configs/config.yaml` 和构建所需源码；秘密不得通过 Dockerfile、构建参数或镜像层交付。

#### 5.3.2 环境变量与网络

Compose 显式列出允许传入容器的应用环境变量，使用无值透传形式，例如 `environment: [HTTP_ADDR, LOG_LEVEL]`。宿主机未设置的变量应在容器中保持未设置，由 YAML 默认配置决定；显式空值必须保留给应用校验。不要使用 `${VAR:-默认值}` 重复应用默认值，也不要将未设置变量转换为空字符串。新增配置映射时同步 Compose 和 README。

可用 `LOG_LEVEL=warn docker compose up -d --build` 覆盖；如操作者使用 Compose 的 `.env` 或 `--env-file`，它们只是部署工具的变量来源，仍需通过 `environment` 显式传入容器，真实值文件不入库。

Compose 仅声明实际需要的服务、端口、卷和依赖，不预置数据库或 Redis。HTTP 容器端口映射须与实际监听地址一致；若覆盖 `HTTP_ADDR`，同步容器目标端口。生产通过反向代理提供公网入口时，宿主机端口绑定回环地址或使用容器内部网络，README 说明实际暴露方式。

HTTP 服务按第 4.4 节提供 `/metrics`，Compose 网络或代理配置明确采集方如何访问及允许的访问范围，README 记录采集地址。默认不额外创建 Prometheus、Grafana 容器；实际接入已有监控系统或决定自建后再配置采集与告警。

#### 5.3.3 运行与更新

常驻服务使用 `restart: unless-stopped`，日志轮转遵守 [日志规范](references/logging-spec.md)。`stop_grace_period` 默认 `15s`，必须大于应用关闭期限；覆盖 `SHUTDOWN_TIMEOUT` 时同步检查。

README 说明构建、启动、查看日志、停止及更新命令。配置环境变量改变后通过 `docker compose up -d` 重建受影响容器，单独 `restart` 不会更新容器环境。

生产更新保留上一版本源码或镜像及对应环境配置，以便回滚；涉及数据迁移时单独说明兼容性。单副本 Compose 更新允许短暂中断，不承诺零停机。

## 6. 验证与交付

### 6.1 测试真实行为

测试覆盖实际功能的正常、失败和资源清理路径；修复缺陷时增加能重现问题的回归测试。CLI 和 Worker 验证输入、输出、退出状态、取消及资源回收等适用行为。

#### 6.1.1 配置

配置测试调用生产加载逻辑，覆盖仓库默认文件可加载、环境变量优先级、未设置与空值的区别、显式零值/false、非法类型/时长、未知字段、缺失文件、必填项等适用行为。使用临时文件构造错误配置，默认文件路径由入口固定传入，测试不修改仓库配置。

测试通过可注入的环境查询函数隔离输入；使用 `t.Setenv` 时不得并行执行或从并行父测试调用，避免污染其他测试。验证无效配置在监听和外部依赖初始化前失败。

#### 6.1.2 错误处理

错误测试覆盖 `ErrorWrap` 的文案替换与 Unwrap、多层包装后的 `errors.Is/As`、不同分类不误匹配，以及技术故障的底层原因仍可识别。验证 `ErrorUnwrapForUser` 返回公开错误的最外层文案和分类状态，普通错误返回空文案和 0；检查实际公开错误链不混入内部信息。

#### 6.1.3 外部依赖

实际引入外部依赖时，使用可控替身或本地测试服务调用生产适配逻辑，验证以下行为，不依赖真实第三方在线服务：

| 验证项 | 断言 |
| --- | --- |
| 上下文与取消 | 调用方上下文传递到依赖，取消能终止支持上下文的操作，读取完成前上下文未被提前取消 |
| 重试与错误转换 | 按实际启用策略验证次数和退避取消，不重试不满足条件的写操作；第三方认证错误不误报为客户端 401，错误链保留诊断原因 |
| 资源与读写语义 | 请求内容不变、响应体仍可由业务完整读取，Close 和取消有效；成功、失败、启动中途失败及停机均释放所持资源 |

#### 6.1.4 HTTP 服务

HTTP/Gin 服务的测试使用实际路由构造器、中间件和错误出口，只在底层依赖或叶子处理器处注入行为。不要另写一套测试中间件，也不要用测试中自行包装错误的断言代替生产错误链验证。没有业务传播链时仅验证现有边界，待实际引入调用链后补测。

HTTP 服务按实际契约验证以下适用行为：

| 必测行为 | 断言 |
| --- | --- |
| API 契约与请求 ID | 按 [API 规范第 7 节](references/api-spec.md#7-验证)通过实际出口验证请求与响应；合法请求 ID 保留，非法或缺失 ID 替换 |
| 校验器与错误出口 | 校验器配置/调用故障按内部错误处理；验证特殊业务映射、公开错误包装后的分类状态与文案、未知错误及无效映射兜底，业务不变量经业务入口验证 |
| 取消、超时与依赖不可用 | 客户端取消后不提交默认 200；原始请求有效时，内部子操作取消、超时及依赖不可用返回 500，连接不可写时中断；通过真实本地 HTTP 连接验证中断行为 |
| 路由及完成边界 | 尾斜杠或大小写不匹配返回 404，不自动重定向；错误方法返回 405 并保留 Allow；正常无正文响应按最终状态记录，所有路径均有请求 ID 和一次完成记录 |
| panic | 响应前返回 500；后续请求仍可处理 |
| 响应后的 panic | 在响应头已发送、正文未完成时注入 panic，通过真实本地 HTTP 连接确认中断；不追加 JSON、不误记成功，不能只用 ResponseRecorder 证明连接行为 |
| 连接接管（实际使用时） | 握手完成仅统计一次；接管后正常关闭、异常及 panic 均由协议适配层关闭连接，不再写 HTTP 错误响应，断开日志符合日志规范 |
| 生命周期 | 调用生产运行逻辑：监听失败返回、正常关闭成功退出、在途请求可完成、超时强制退出并回收资源；实际使用连接接管时验证停机停止新接管、通知已有连接关闭，期限内完成清理和关闭日志，逾期强制关闭且不无限等待 |

使用 `httptest` 和本地临时监听地址 `127.0.0.1:0`，测试自行启动和关闭服务，不依赖外部运行实例。通过可注入停止信号测试生命周期，使用同步条件和有界超时，不用 sleep 猜测时序。上述测试纳入普通测试集，不因缺少外部 URL 而跳过。

#### 6.1.5 运行指标

使用生产中间件和独立 Registry 验证正常、拒绝、失败、取消、超时及 panic 路径：在第 4.2 节的完成边界，Counter 和 Histogram 仅记录一次，Gauge 仅递减一次；Histogram 使用秒。用同步控制验证请求进入后 Gauge 递增、到达完成边界后归零。普通 HTTP 响应提交后失败的实际 status 与 outcome 保持一致；实际使用连接接管时，保持连接打开，验证握手完成即结束 HTTP 统计，后续处理器退出或连接关闭不重复计数、不改变握手结果。

访问同一路由的不同资源 ID、随机不存在路径和未知方法，确认标签归一化且时间序列数量不随动态输入增长。请求 `/metrics` 能获取库的标准指标格式和已注册采集器，采集本身不增加应用请求指标；反复构造、关闭测试服务不发生重复注册。以上验证不要求外部 Prometheus 或 Grafana 实例，实际部署告警的验证按第 4.4 节执行。

### 6.2 检查命令

命令实现集中维护在项目 Makefile。使用 GNU Make 和 POSIX shell，从工程根目录运行以下六个入口，默认目标为 `test`：

| 目标 | 用途 |
| --- | --- |
| `make build` | 构建 `cmd/$(SERVICE)` 到 `bin/$(SERVICE)`；发布时指定可追溯的 `VERSION` |
| `make run` | 构建并前台运行所选服务 |
| `make dev` | 构建后加载根目录 `.env` 并前台运行所选服务；加载规则见第 3.2 节 |
| `make fmt` | 修复 Go 源码格式 |
| `make test` | 运行整个模块的行为测试，不使用测试结果缓存 |
| `make coverage` | 运行整个模块的测试，生成覆盖率文件并输出函数级及总覆盖率 |

`build`、`run`、`dev` 默认选择 `SERVICE` 指定的服务，可用 `make build SERVICE=orders-worker`、`make run SERVICE=orders-worker` 或 `make dev SERVICE=orders-worker` 切换。`dev` 使用 exec 启动程序，保留退出状态和信号处理语义；其他目标不加载 `.env`。

`test` 和 `coverage` 共用 `GO_TEST_FLAGS ?= -count=1 -v -timeout=5m -json`，默认禁用测试结果缓存、输出详细 JSON 测试事件，每个包的测试超时为 5 分钟。可通过 `make test GO_TEST_FLAGS='-count=1 -timeout=5m'` 等方式覆盖参数。

`fmt` 直接修改 Go 源码格式，跳过 `.git`、`.tools` 和 `vendor` 目录。三个验证入口不额外执行依赖校验、模块一致性检查、独立编译检查或静态分析，也不安装额外工具。

`coverage` 使用 atomic 覆盖率模式，在工程根目录生成 `coverage.out`，并输出函数级及总语句覆盖率，不设置统一覆盖率门槛。可用 `go tool cover -html=coverage.out` 查看源码覆盖情况；覆盖率统计不能替代第 6.1 节的行为验证。

### 6.3 验证流程与交付记录

初始化必须通过 `fmt`、`coverage`、`build`，并验证运行中的程序行为；HTTP 服务使用实际功能请求。后续变更执行 `fmt` 和相关测试，需要覆盖率时执行 `coverage`；错误、日志或并发改动需补充反例测试。`coverage` 已包含测试，无需为同次验收再运行 `test`。漏洞扫描由项目发布流程另行配置。

服务初始化及配置或部署变更还需执行 `docker compose config --quiet`、镜像构建和容器运行验证。使用独立 Compose 项目名及可用本地端口，验证镜像内默认配置存在、非 root 运行、环境变量未设置时保留默认值、有效覆盖生效、非法覆盖导致启动失败，以及 SIGTERM 能在宽限期内正常关闭。HTTP 服务请求实际接口（初始为 ping）；仅容器处于运行状态不算可用性通过。

失败场景临时关闭自动重启，便于核对退出码；检查结束清理本次启动的容器和网络，不影响已有部署。

缺少工具或环境能力时明确失败，交付标明未执行项，不绕过或降级检查。记录源码及工具版本、执行命令、实际结果、运行入口和必要偏离；人工复核职责边界、抽象必要性及日志的诊断价值。
